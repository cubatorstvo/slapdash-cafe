1. Алгоритм работы:

Через подключённый GitHub получи текущий SHA main.

Прочитай из main все файлы, связанные с задачей. Используй поиск по репозиторию и fetch_file, а не догадки по старому контексту.

Создай временную ветку, например:
work/<короткое-название-задачи>
от текущего main.

Вноси изменения в эту ветку. Для крупной задачи желательно добавить отдельный regression-test, воспроизводящий именно требуемое поведение.

Для реальной проверки используй GitHub Actions на ubuntu-24.04: скачай официальный Godot 4.7 stable, сделай headless import/parse, затем запусти целевые тесты.

При необходимости запускай сам проект headless несколько секунд, чтобы поймать runtime errors, которые не видны при одном import.

Если тест упал, сначала изучи полный job log и исправь причину. Не пушь в main, пока целевой тест и разумный regression-набор не зелёные.

После зелёного прогона создай чистую ветку:
sol/<task>-final
от того SHA main, на котором начиналась работа, и положи туда только реальные изменения проекта и нужные тесты. Временные .github/workflows/..., debug-файлы и диагностические скрипты в итоговый commit не включай.

Сравни:
main...sol/<task>-final.
Перед обновлением main должно быть:
ahead_by = 1 или ожидаемое число коммитов,
behind_by = 0.

Обновляй main только fast-forward, force=false.

После push снова прочитай branch main и убедись, что он действительно указывает на новый полный 40-символьный SHA.

В ответе пользователю укажи commit SHA, что именно изменено и какие тесты реально прошли.

ВАЖНО: другой агент/чат может одновременно менять репозиторий. Поэтому непосредственно перед fast-forward ещё раз проверь текущий main. Если main уже изменился, не форси старую ветку поверх новых изменений. Возьми новый main, перенеси изменения, заново прогони тесты и только потом пушь.

GitHub является source of truth. Перед каждой задачей сначала получай актуальный main из GitHub и работай именно от него.

Локальные копии проекта в окружении могут быть устаревшими — не используй их как исходную версию без проверки SHA против GitHub.

2. Основную разработку и тесты вести только в локальной среде у себя на сервере, не делегировать на git actions (слишком много итераций при разработке через actions). Через actions можно только запускать итоговые CI-тесты, но не как замену локальным тестам, а как дополнительная проверка. 

3. Если у тебя нет в локальном окружении годот 4.7.2, то найди его в Library (файл Godot_v4.7.2-stable_linux.x86_64.zip) и установи. Если файл не найден, прекрати работу и сообщи об этом.
