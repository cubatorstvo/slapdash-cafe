# P5.06 — управление учебными задачами и объяснениями

## База

- `main` при начале и повторной сверке: `a86351254a36beed8b1fad9aef622e15ba477c5b`.
- P5.05 присутствует в этой базе: `FeatureAccess`, `ProgressionDirector`, каталог и `CafeJourney` уже слиты.
- Реализация не вводит второй граф анлоков и не меняет условия звёзд, цены или награды.

## Одна текущая задача

Владельцем текущей цели остаётся `scripts/cafe_journey.gd::current`. HUD уже показывает ровно один его `title/detail`, поэтому отдельная цель на компьютере не добавлялась. `CafeJourney` продолжает пересчитываться по реальному состоянию кафе, пропускает уже выполненные шаги и возвращает существующую точку действия/конкретное временное препятствие. `LearningPacing.current_task()` является тонким делегатом к тому же `CafeJourney.current`, а не альтернативным списком шагов.

Целевой тест `tests/test_p5_pacing.gd` отдельно фиксирует выбор первого незавершённого шага, пропуск уже полученной формулы и переход в состояние ожидания доставки.

## Источники фактов

Общие факты берутся только из действующего `progress.feature_progress`, который публикует `ProgressionDirector`:

- `cafe_id` — устойчивый идентификатор текущего кафе;
- `unlocked_features` — уже разрешённые механики/наборы;
- `milestones` — подтверждённые доменные события.

Для объяснений используются подтверждённые факты текущего графа: `first_clone_created`, `first_live_lesson_accepted`, `first_auto_served`, `first_masterclass_saved`, `first_video_training_completed`, `first_group_training_completed` и реальные feature IDs поздних наборов. Чтение сообщения не записывает milestone и не участвует в `FeatureAccess`.

## Очередь объяснений

`scripts/progression/learning_pacing_core.gd` содержит один детерминированный порядок объяснений: сначала 1★, затем распространение способов, специализация и координация. Один элемент описывает общий смысл набора и может слушать несколько feature IDs; поэтому одновременное открытие нескольких предметов/возможностей одного набора создаёт одно сообщение.

Алгоритм:

1. Снимок `unlocked_features/milestones` переводится в множества.
2. При изменении снимка просматривается фиксированный массив объяснений по порядку графа.
3. В очередь добавляется только впервые ставший применимым стабильный `id`.
4. `seen` и уже поставленные в очередь ID исключают дубликаты.
5. Видимым может быть только первый элемент очереди. `F1` отмечает его просмотренным и освобождает место следующему.
6. При первом входе в уже развитое кафе старая история не проигрывается подряд: применимые старые элементы сворачиваются, ранние помечаются как пропущенный catch-up, а пользователю остаётся максимум одно наиболее позднее актуальное объяснение.
7. При обычной повторной загрузке незакрытая локальная очередь восстанавливается, а не строится заново из истории.

## Подходящий момент

Показ не использует задержку по времени. `learning_pacing_runtime.gd` строит состояние из действующих runtime-фактов и показывает панель только при `world` UI mode.

Блокирующие состояния:

- `CafeUiMode.resolve(game) != WORLD` — компьютер, книга, инструмент, пауза и остальные модальные режимы;
- `game.input_blocked()`;
- перенос/удержание предмета (`anchored_item`);
- активная готовка;
- активный личный урок;
- подтверждение результата подачи;
- активная инспекция/визит;
- локальный сон или общая сцена сна;
- занятая строка срочного `HUD.notice`.

Когда блокировка исчезает, тот же первый элемент очереди снова становится доступен. Автоматическая работа других столов сама по себе не блокирует свободного игрока.

## Локальный seen и кооператив

Общий прогресс по-прежнему принадлежит кафе/хосту. Локальное состояние объяснений хранится отдельно в `user://p5_learning_pacing.cfg` под ключом `cafe:<cafe_id>:player:<player_key>`:

- `player_key` создаётся один раз в локальном профиле и затем стабилен; сетевой peer ID не используется;
- `seen` хранит просмотренные стабильные ID;
- `pending` хранит текущий и ожидающие ID, поэтому загрузка того же кафе не теряет непросмотренное сообщение;
- смена `cafe_id` очищает runtime-очередь и переключает её на другой namespace.

Каждый клиент вычисляет безопасный момент локально из собственного UI/переноски/обучения/сна. Поэтому занятый игрок не подавляет сообщение у свободного. Анлоки при этом читаются из общего авторитетного snapshot и не зависят от локального seen.

## UI

Новая сцена UI не создавалась и существующие сцены не менялись. Runtime создаёт компактную немодальную `PanelContainer` поверх HUD, применяя действующую `CafeStyle.make()`. Панель не принимает мышь и не скрывает/заменяет строку денег, event feed или текущую задачу. Скриншоты по условию контракта не приложены, так как сцены UI не менялись.

## Проверки

Добавлен `tests/test_p5_pacing.gd`, который проверяет:

- выбор текущей задачи и пропуск уже завершённого шага;
- состояние до первой автоподачи и одно объяснение после подтверждённой автоподачи;
- отсутствие повторов для queued/seen стабильного ID;
- состояние до/после первого реально завершённого видеоурока;
- объединение трёх поздних feature-анлоков в одно объяснение;
- сворачивание старой истории при входе в развитое кафе;
- блокировку при переноске, готовке, уроке, подтверждении, инспекции, сне, срочном notice и любом не-world UI mode.

Локально использован Godot `4.7.2.stable.official.ed1daf0bf` из Library с изолированными `HOME/XDG_CACHE_HOME/XDG_DATA_HOME`:

- изолированный прогон `learning_pacing_core.gd`: `PASS local pacing core`;
- компиляция/создание `learning_pacing_runtime.gd` с минимальными заглушками внешних зависимостей: `PASS local pacing runtime parse`.

Полный проектный тест-раннер локально не запускался: GitHub доступен через подключённый коннектор, а прямой checkout репозитория из контейнера заблокирован сетевой средой. GitHub Actions намеренно не использовались. Физический глобальный прогон кафе контракт P5.06 не требует.
